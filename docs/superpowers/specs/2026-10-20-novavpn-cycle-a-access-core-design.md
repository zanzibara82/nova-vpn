# NovaVPN — цикл A: ядро доступа

**Статус:** принят к планированию. Проектная спецификация этапа 1 + этапа 2 из ТЗ §17.
**Дата:** 2026-10-20. **ТЗ:** NovaVPN v1.0 (`NovaVPN_prompt_ru.pdf`, 19 разделов).
**Окружение, проверенное при проектировании:** Windows 11 10.0.26300; Docker Desktop 29.8.2 + Compose v5.6.0; WSL2 Ubuntu 26.04, ядро `6.18.54.1-microsoft-standard-WSL2` с `CONFIG_WIREGUARD=m`, `CONFIG_TUN=m`, `/dev/net/tun` доступен; Go, PostgreSQL, Terraform, Ansible на хосте отсутствуют.

## 1. Границы цикла и критерии приёмки

### 1.1 В объёме A

Рабочая выдача и отзыв VPN-доступа через настоящий WireGuard-туннель: репозиторий, Go control plane (модульный монолит), миграции PostgreSQL, публичный API, `novavpn-node-agent`, локальный test harness с привилегированным WireGuard-узлом в контейнере, проверки маршрутизации/DNS/IPv6, автоматические тесты, Ansible-роль узла, CI.

### 1.2 Вне объёма A (перенесено осознанно)

| Уходит в | Что | В A существует как |
|---|---|---|
| B | подбор сервера, балансировка, failover, избранное/недавнее | поля `latency_ms`, `load`, `availability` в контракте каталога со статусом «не измерено» |
| C | веб-панель пользователя, admin UI, карта, темы, a11y, локализация | OpenAPI-контракт, из которого панель будет потребитель |
| D | подтверждение email, восстановление доступа, тарифы, платёжный провайдер (глобальный рынок), вебхуки, возвраты, экспорт данных | таблицы `subscription_plans` / `subscriptions` с одним внутренней планкой; эндпоинты отсутствуют |
| E | GUI-клиент Windows (первый клиент), привилегированный локальный хелпер, kill switch на клиенте | CLI-тест-клиент на том же слое выдачи конфигов |
| F | MFA админов, подписанные обновления, Terraform, Prometheus/Grafana/Loki, нагрузочные испытания на реальной инфраструктуре, бэкапы, DR | поля схемы и место в структуре репозитория |

В перенесённых частях не создаётся ни заглушек, ни пустых директорий: ТЗ §19.3 запрещает фиктивные реализации вместо работающей логики.

### 1.3 Критерии приёмки A (подмножество ТЗ §18)

1. Аккаунт создаётся, сессия живёт, refresh ротируется, отозванная семья refresh не обновляется.
2. Устройство регистрируется по публичному ключу; приватный ключ устройства ни разу не появляется в HTTP-трафике (проверяется ассертом на фикстурах).
3. Профиль выдаётся, туннель **фактически передаёт трафик** через узел, egress-адрес совпадает с адресом узла.
4. Отзыв профиля снимает пиера на узле за ≤ 30 с и трафик через туннель останавливается.
5. Достигнут лимит устройств по тарифу → `409 device_limit_reached`, а не молчаливая выдача.
6. Ротация ключа не рвёт соединение: старый пиер живёт в overlap-окне, новый handshake наблюдён, старый снят.
7. DNS-запрос клиента разрешается через recursor узла; off-tunnel резолв не наблюдается.
8. IPv6-утечки нет при включённой политике из раздела 8.
9. Миграции выполняются `up → down → up` без потерь.
10. Отозванный/просроченный профиль не попадает в desired set ни при каких условиях (проверяется свойством, а не примером).
11. `go test ./...`, интеграционные и e2e-прогоны зелёные; CI-запись содержит явный маркер `not-run` для того, что не выполнялось.

## 2. Модель угроз (ТЗ §17, этап 1)

Активы: (A1) конфиденциальность трафика пользователя, (A2) приватные ключи узлов, (A3) учётные данные и токены доступа, (A4) доступность control plane и узлов, (A5) корректность границ тарифа.

| Противник | Вектор | Мера в A | Остаточный риск |
|---|---|---|---|
| Хостинг-провайдер узла с root-доступом к диску | чтение приватного ключа узла из файла `0600`, расшифровка трафика своего узла | ключ не покидает узел; на узле нет ни данных других клиентов, ни журнала содержимого; детект дрейфа конфигурации | **Компрометация одного узла раскрывает трафик, идущий через него в моменте.** Это неотъемлемое свойство топологии с одним hop (single-hop), а не наше упущение. Multi-hop и распределение доверия — вне A |
| Сетевой противник на пути | пассивное чтение, активная подмена | WireGuard (curve25519 / chacha20-poly1305 / blake2s — штатная криптография, ТЗ §19.6); TLS к API с обязательной проверкой сертификата (ТЗ §19.8) | пост-квантовая стойкость отсутствует; анализ трафика (объёмы, тайминги) не отсекается |
| Злоупотребляющий пользователь | спам ключами, обход лимита устройств, повторяющиеся выдачи | rate limit, argon2id, валидация каноничности ключа, уникальный индекс на активный профиль, лимит устройств | WireGuard не умеет отказывать в handshake по квоте, см. раздел 7.4 — квота по одновременным сессиям обеспечена с задержкой |
| Подбор паролей | credential stuffing | rate limit по IP и по аккаунту, прогрессивная задержка, блокировка по admin-причине | вектор закрывается полностью в F (MFA для входа админов) |
| Компрометированный админ | отзыв чужих ключей, вывод узла | аудит каждой админ-операции с причиной, отдельная роль, MFA (F) | |
| Скомпрометированный ответ API | инъекция в конфигурацию клиента/узла | серверные строки не попадают в shell: конфиг парсится в структуру и пересобирается; жёсткие паттерны на host/ключ/CIDR/порт/MRU; тест на shell-метасимволы и CRLF | |
| Узел-самозванец | запрос desired set чужого узла | per-node bearer-токен, хэш в БД, обязательный TLS, опциональное закрепление CA; отзыв токена мгновенен | |

Отдельно, чтобы это не потерялось: **содержимое трафика, посещённые URL и DNS-запросы не пишутся ни в одну базу и ни в один журнал** (ТЗ §11). unbound на узле конфигурируется с `log-queries: no`, и это проверяется тестом роли, а не оставлено как рекомендация.

## 3. Компоненты и границы доверия

```
[клиент: устройство пользователя]
   приватный ключ устройства — только на устройстве
        | HTTPS + JWT (публичный API)
        v
[novavpn-api]  модульный монолит, N экземпляров
   PostgreSQL (источник истины) + Redis (rate limit, denylist access-токенов, дельты счётчиков)
        ^ HTTPS + per-node bearer (исходящие запросы от узла; входящих на узел нет)
        |
[novavpn-node-agent] systemd, нон-root, CAP_NET_ADMIN|CAP_NET_RAW
   ├── keys        генерация и хранение приватного ключа узла (0600), наружу не отдаёт
   ├── provisioner desired set → netlink diff-apply
   └── collector   факты (handshake, байты, host-нагрузка) → API
        | netlink (wgctrl-go)
        v
   [ядро WireGuard] + [nftables: отдельная table NAT] + [unbound]
```

Три правила границ, из которых дальше всё следует:

1. **Приватный ключ узла генерируется на узле и никогда его не покидает.** Control plane знает только публичный ключ узла. Требование ТЗ §5 «backend не передаёт клиентам приватные ключи серверов» выполняется отсутствием данных, а не политикой.
2. **Узел инициирует все соединения сам.** Административного входа на узел из интернета нет; ТЗ §5 («узкий привилегированный компонент вместо shell из веб-запросов») выполняется архитектурно: сетевые изменения делает локальный агент, а не API.
3. **Квота и адреса — только в control plane.** Единственный, кто видит все узлы и весь тариф, — БД; гарантия уникальности адреса существует как ограничение БД, а не как проверка в коде.

Модули Go (`internal/`): `auth` (argon2id, JWT, refresh-ротация, denylist), `devices` (регистрация, ротация с overlap), `entitlements` (план → права, без платежей), `servers` (каталог, регистрация узлов, вычисление desired set), `connections` (выдача/отзыв профилей, аллокация адресов, события), `nodeapi` (контракт с узлом), `telemetry` (свёртка наблюдений в агрегаты), `audit`, `db` (sqlc), `httpx` (envelope, request id, rate limit, идемпотентность).

## 4. Контракт control plane ↔ узел

### 4.1 Эндпоинты

Все — `application/json`, только HTTPS. Префикс `/internal/v1`. Аутентификация: `Authorization: Bearer <node_token>`.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/internal/v1/nodes/enroll` | `bootstrap_token` (одноразовый, выдаётся admin) + публичный ключ узла → `node_token` |
| GET | `/internal/v1/nodes/{server_id}/desired` | desired set; `If-None-Match` → `304` |
| POST | `/internal/v1/nodes/{server_id}/observed` | применённая конфигурация + факты по пиерам и интерфейсу |
| POST | `/internal/v1/nodes/{server_id}/heartbeat` | версия агента, uptime, состояние применения |
| POST | `/internal/v1/nodes/{server_id}/token/rotate` | узел сам меняет свой токен (ротация без участия человека) |

Answer `desired`:

```json
{
  "server_id": "8f0c…",
  "config_version": 1047,
  "mtu": 1420,
  "listen_port": 51820,
  "dns_servers": ["10.99.0.1"],
  "keepalive_sec": 25,
  "peers": [
    {
      "public_key": "wTpN…=",
      "allowed_ips": ["10.99.7.42/32"],
      "expires_at": "2026-11-19T10:00:00Z",
      "state": "active"
    }
  ],
  "measured_at": "2026-10-20T10:00:03Z"
}
```

`peers` содержит только `state in {active, rotating_old_key}`. Просроченный, отозванный, `superseded` c закрытым overlap — отсутствуют. Ни приватных ключей, ни DNS-запросов, ни имён пользователей в этом ответе нет.

### 4.2 Применение: diff, а не full replace

Закрыто измерениями S3 (2026-10-20): [ADR-004](../../adr/0004-wireguard-peer-apply.md), журнал —
[docs/spikes/2026-10-20-s1-s3-wireguard-netlink.md](../../spikes/2026-10-20-s1-s3-wireguard-netlink.md).

Факт, который определил дизайн: `ConfigureDevice(ReplacePeers=true)` **пересоздаёт каждого
пиера**, даже когда отправленная конфигурация байт-в-байт совпадает с живой. В A/B-прогоне
неизменённый пиер, несущий непрерывный трафик, переподключался в 12/12 циклов, а его
счётчики rx/tx откатывались назад в 4/12. Тот же цикл per-peer операциями — 0/12
переподключений и монотонные счётчики. Потерь ICMP не было ни в одном режиме, поэтому
аргумент против full replace не «обрыв соединения», а handshake-церемониал на каждом цикле
и уничтожение байтовой телеметрии, на которой держатся ADR-006 и «распределение нагрузки»
из ТЗ §9.

Правила `provisioner` (полная формулировка — в ADR-004):

- `Config.ReplacePeers` — всегда `false`, включая первое применение: пустое live-множество
  означает, что дельта равна всему desired, и пиеры добавляются per-peer операциями.
- Сравнение desired↔live по нормализованным полям пиера (публичный ключ, endpoint,
  множество allowed-IP, persistent-keepalive). Совпавший пиер в netlink не отправляется.
- Отзыв — `PeerConfig{PublicKey: …, Remove: true}`. Измерено: набор 2 → 1 за ~0.5 мс,
  соседний пиер сохраняет handshake и счётчики, маршрут до отозванного адреса
  становится недоступен немедленно (`Destination Host Unreachable`), повторная выдача
  восстанавливает связность в том же цикле.
- Счётчики снимаются **до** применения изменений: пересоздание пиера обнуляет rx/tx в ядре.

WireGuard-устройство создаётся через rtnetlink (`ip link add dev wg0 type wireguard`) —
в зафиксированной версии `wgctrl` нет `AddDevice`. Прямой `genetlink` не нужен: фоллбэк,
заложенный в предыдущей редакции этого раздела, снят по итогам S3, потому что библиотека
умеет и штучное удаление, и штучное обновление (`Remove`, `UpdateOnly`, `ReplaceAllowedIPs`),
и по поведению совпадает с `wg(8)`.

### 4.3 Тайминги и поведение при отказах

Интервал desired-poll — 30 с, jitter ±10 %, long-poll не используется (нет ценности при уже выбранном 30 с и он держал бы соединение открытым на каждом узле).

| Отказ | Поведение |
|---|---|
| API недоступен | узел **хранит последнее применённое состояние** и продолжает обслуживать текущих клиентов; репортит `applied_config_version` с `stale=true`. Никаких «догадок» о desired set |
| desired > 5 мин не получен | узел не удаляет пиеров; `availability` в каталоге становится `unknown` |
| узел не присылал heartbeat 3 интервала | `server_health.status='stale'`, узел исключается из подбора (B) |
| Redis недоступен | rate limiter на публичных маршрутах — **fail-open** с записью в журнал; узловые маршруты продолжают работать. Обоснование: отказ Redis не должен отрезать пользователей от уже выданного VPN-доступа |
| узел выводится из эксплуатации | `PATCH …/maintenance` → `state='draining'` → desired пустеет, узел снимает всех; активные клиенты получают понятную ошибку, а не тишину |

Отзыв, сделанный пока узел был недоступен, применится при его возвращении. Это реальное ограничение pull-модели и оно записано в разделе 13, а не замолчано.

### 4.4 TLS

Узел проверяет сертификат API через системное доверие; опционально `NOVAVPN_API_CA_FILE` (закрепление CA). Флаг пропуска проверки существует только в dev-harness и **жестко отказывается**, если `NOVAVPN_ENV != dev` (ТЗ §19.8).

## 5. Публичный API

Префикс `/api/v1` (ТЗ §10: версионирование). `api-spec/openapi.yaml` — источник истины по формам ответов, кодам ошибок и обязательности заголовков. Маршрутизация через `oapi-codegen` не генерируется: генератор добавляет собственный слой валидации с отдельным форматом ошибок, а §5.2 требует единый envelope на всех маршрутах, включая транспортные отказы. Соответствие живых ответов схемам проверяется тестом (задача 19), а не eyeball-ревью.

### 5.1 Маршруты цикла A

| Метод | Путь | Примечание |
|---|---|---|
| POST | `/auth/register`, `/auth/login` | email + пароль; подтверждение email — цикл D |
| POST | `/auth/refresh` | ротация refresh; повторное использование → отзыв всей семьи |
| POST | `/auth/logout` | отзыв семьи refresh |
| GET | `/me` | пользователь, план, использование устройств |
| POST/GET | `/devices` | регистрация по публичному ключу |
| DELETE | `/devices/{id}` | отзыв устройства = отзыв всех его профилей |
| POST | `/devices/{id}/keys/rotate` | новое имя + overlap-окно |
| GET | `/servers` | каталог; неизмеренные поля — `null`, не `0` |
| POST | `/devices/{id}/profiles` | выдача профиля на сервер |
| GET | `/devices/{id}/profiles` | список с `status`, `expires_at` |
| DELETE | `/devices/{id}/profiles/{server_id}` | отзыв |
| GET | `/devices/{id}/profiles/{server_id}/config` | готовый `[Interface]`/`[Peer]` текст |
| POST | `/api/v1/admin/…` | серверы, отзыв токена узла, блокировка пользователя с причиной, аудит |

### 5.2 Сквозные требования ТЗ §10

- **Единый формат ошибки:** `{"error":{"code":"device_limit_reached","message":"…","details":{…},"request_id":"…"}}`. Коды стабильны и документированы в OpenAPI; `request_id` совпадает с journal entry.
- **Язык сообщений:** продукт русскоязычный (решение 2026-10-22) — сообщения прикладного HTTP-слоя (регистрация, вход, устройства) пишутся по-русски; инфраструктурные строки middleware (идемпотентность, лимиты) остаются английскими, клиенты ориентируются на стабильные коды; `locale` по умолчанию — `ru` (раздел 6).
- **Идемпотентность критических операций:** `Idempotency-Key` обязателен на `POST /devices`, `POST …/profiles`, `…/keys/rotate`. Повтор с тем же ключом возвращает первый результат; конфликт тела с сохранённым — `409 idempotency_key_conflict`; повтор с тем же ключом, пока первый запрос не завершён, — `409 idempotency_key_in_progress`.
- **Авторизация** на всех маршрутах, кроме register/login/refresh; проверка права на объект, а не только факта аутентификации (матрица «роль × маршрут» как тест — ТЗ §10 и ТЗ §14).
- **Rate limiting:** login/register — по IP и по аккаунту с прогрессивной задержкой; выдача профилей — 30/мин на пользователя; узловый префикс — по узлу. Redis token bucket, fail-open (раздел 4.3).
- **Валидация входа:** ключ устройства — base64 32 байта с проверкой каноничности (перекодировка равна исходной); `platform` — enum; CIDR/порт/MTU — диапазоны.
- **Журналирование:** request id, маршрут, статус, длительность, user id. Никаких токенов, паролей, приватных ключей, заголовков авторизации и query-строк с секретами (ТЗ §10, ТЗ §15).

### 5.3 Сессии

Access — короткоживущий JWT (TTL 10 мин, `jti`), refresh — непрозрачный токен с ротацией; отозванные access — denylist в Redis с TTL по `exp`; семья refresh отзывается durable-записью в PostgreSQL. Обоснование разделения: мгновенный отзыв влияет на новые выдачи, а уже выданный access живёт не дольше 10 минут, и критичный для безопасности «забрать доступ к трафику» делает не токен, а снятие пиера на узле (раздел 7.4). Потеря Redis после ребута стоит пере-наполнить из families, отозванных позже самого старого живого `jti`, — это процедура, а не надежда.

## 6. Модель данных (ТЗ §11)

Инструменты: `golang-migrate` (артефакты `migrations/NNNN_name.up.sql` / `.down.sql`), запросы — `sqlc`. Ниже — существенные ограничения, а не пересказ CREATE TABLE.

| Таблица | Ключевые ограничения и зачем |
|---|---|
| `users` | `email citext unique`; `password_hash`; `status enum('active','locked','deleted')`; `locked_reason` (для ТЗ §9); `email_verified_at` (заполняется в D); `locale` (ru по умолчанию) |
| `devices` | `public_key` канонический base64; `unique(user_id, public_key)`; `revoked_at`; `rotation_of device_id` — ссылка на предка для overlap; `platform` |
| `refresh_token_families` | `family_id`, `current_token_hash unique`, `revoked_at`, `ip inet null` (только для анти-злоупотреблений, retention 90 дн.) |
| `server_locations` | `country_code`, `city`, `lat numeric(9,6)`, `lon numeric(9,6)`, `timezone` — координаты для карты (C), данные каталога с A |
| `vpn_servers` | `advertised_host`, `listen_port`, `public_key unique`, `address_pool_v4 cidr`, `mtu`, `dns_mode enum('local_recursor')`, `config_version bigint`, `maintenance_status enum('online','draining','maintenance','retired')`, `provider`, `region`, `capacity_mbps integer null` — **заявленная пропускная способность, а не измеренная**; поле честного происхождения описано в ADR-006 |
| `node_credentials` | `token_hash unique` (sha256 от высокоэнтропийного секрета), `issued_at`, `last_used_at`, `revoked_at` — приватного ключа узла в БД нет и не будет |
| `vpn_profiles` | `unique index on (device_id, server_id) where status='active'` — двойная выдача невозможна на уровне БД; `status enum('active','superseded','revoked','expired')`; `expires_at`; `overlap_valid_until` (ротация); `address_v4 inet` |
| `tunnel_addresses` | `primary key (server_id, address)`; аллокация под блокировкой строки сервера → коллизия адреса невозможна конструктивно |
| `subscription_plans` | `slug`, `device_limit`, `server_selector`, `traffic_quota_bytes null = безлимит`, `trial_days` — в A один план `internal-default` |
| `subscriptions` | `user_id`, `plan_id`, `status`, `starts_at`, `ends_at`, `source enum('manual','trial','billing')` — `billing` появится в D |
| `server_health` | `server_id`, `observed_at`, `peers_configured`, `peers_handshaked`, `interface_rx/tx_bytes`, `load1`, `cpu_pct`, `applied_config_version`, `status enum('ok','stale','error')` |
| `connection_events` | `event enum('profile_issued','profile_revoked','profile_expired','peer_applied','peer_removed','handshake_observed','handshake_failed','node_stale','connection_error')`, `detail jsonb` — **только коды ошибок и версии, не содержимое трафика** |
| `device_day_traffic` | `pk(user_id, device_id, day)`, `rx_bytes`, `tx_bytes` — единственный персистентный след объёмов (решение: агрегат на устройство-сутки) |
| `admin_users`, `admin_audit_logs` | `admin_audit_logs(admin_id, action, target_type, target_id, reason not null, created_at)` |
| `idempotency_keys` | `unique(user_id, route, idem_key)`; `request_hash` — sha256 тела, по нему определяется конфликт содержимого при повторе ключа; `response_status`/`response_body` и `completed_at` — различают «запрос в полёте» от готового ответа. **Появилась на этапе планирования цикла A-1:** без неё заголовку `Idempotency-Key` из §5.2 негде храниться |
| `bootstrap_tokens` | `token_hash unique` (sha256 от высокоэнтропийного секрета), `server_id`, `expires_at`, `used_at`, `revoked_at` — одноразовый токен для enroll узла (§4.1); приватного ключа узла здесь нет. **Появился на этапе планирования цикла A-1** |

**Счётчики байт по пиерам** из отчёта узла нужны для расчёта загрузки и дельт, но в БД не лежат: хранятся как мгновенные значения в Redis с TTL и сворачиваются в `device_day_traffic`. Так «нагрузка узла» (ТЗ §4) доступна, а пер-сессонный лог объёмов — нет.

**Retention:** `connection_events` и `refresh_token_families.ip` — 90 дней по умолчанию, ежедневная задача очистки; удаление по пользователю — отдельная операция (механизм данных для ТЗ §7 «удаление аккаунта и связанных данных» и ТЗ §11 «возможность удаления»). Партиционирование помесячно отложено до реальных объёмов (F) и зафиксировано как отложенное, а не «потом само».

## 7. Ключевые последовательности

### 7.1 Выдача профиля

Проверка права → entitlement (сервер входит в план) → лимит устройств → сервер `online` → аллокация адреса под блокировкой → `insert vpn_profiles` → `config_version++` → ответ с конфигурацией.

Узел применит desired на следующем опросе (≤ 30 с). **API не сообщает клиенту, что туннель работает** — он сообщает, что профиль выдан. Клиент обязан сам дождаться handshake и честно отобразить промежуточное состояние `waiting_for_peer_apply`. Это прямое следствие ТЗ §19.12 («не заявляй о завершении функции, пока она не реализована и не проверена»).

### 7.2 Отзыв профиля

`status='revoked'` → адрес помечается освобождаемым с окном повторного использования 5 минут (защита от ситуации «новый клиент получил адрес старого, у которого ещё живы кэшированные маршруты» на пути) → `config_version++` → узел снимает пиера → отчётирует `peer_removed`.

### 7.3 Ротация ключа с overlap (ТЗ §5 «с учётом совместимости клиента»)

Клиент генерирует новую пару на устройстве → `POST …/keys/rotate` с новым публичным ключом → создаётся устройство-потомок (`rotation_of = предок`), профиль переносится на потомка с тем же адресом (смена ключа не меняет IP клиента — иначе любая ротация рвала бы соединения) → предок получает `state='rotating_old_key'` и `overlap_valid_until = now() + 10 min` → desired содержит оба ключа → как только агент наблюдал handshake от нового ключа, старый снимается немедленно → по истечении окна старый снимается в любом случае.

### 7.4 Лимит устройств (ТЗ §5)

Жёсткая часть: `count(devices where revoked_at is null)` по лимиту entitlement — гарантировано БД. Конечная часть: «одновременно подключённых» узлы видят локально, control plane узнаёт из отчётов; превышение → излишние пиеры помечаются к снятию по LRU(последний handshake) и уходят в течение интервала синхронизации. Мгновенно отказать лишнему соединению WireGuard не может, и это ограничение, а не задача «доделать».

### 7.5 Незапланированная недоступность узла

Узел молчит > 3 интервалов → `server_health.status='stale'` → каталог отдаёт `availability='unknown'` → подбор (B) его исключает → активные клиенты видят `connection_error` с рекомендацией, а не «защищено».

### 7.6 Вывод узла из эксплуатации

`draining` → desired пуст → узел снимает всех; при вытеснении сервера админ видит число активных пиеров до подтверждения. Удаление сервера из каталога возможно только при `peers_active = 0`.

## 8. Приватность, DNS, IPv6, kill switch

**DNS.** На узле стоит unbound как рекурсор для клиентов (`log-queries: no`), исходящий DNS с узла наружу закрыт, кроме служебного разрешения имён самого узла. Клиенту в `[Interface] DNS =` отдаётся адрес recursor в туннеле; AllowedIPs по умолчанию `0.0.0.0/0`. ТЗ §6 «исключи утечки DNS за пределы туннеля» проверяется тестом harness, а не декларацией.

**IPv6.** Политика цикла A: на время подключения IPv6 на клиенте отключается. Это даёт гарантированное отсутствие IPv6-утечки без NAT66 и без требований к префиксу от хостинга. Ограничение фиксируется явно и показывается в UI: **на IPv6-only сетях клиент останется без доступа** (на мобильные сети это реально). IPv6 в туннеле через ULA + NAT66 — отложённое решение, требует выделенного префикса на узле, ADR-007.

**Kill switch.** Относится к клиенту (цикл E) и к узлу (не нужен). В A определяется только контракт: состояние kill switch — это наблюдаемое свойство, а не строка текста; UI обязан отличать «включён и активен» от «включён, но не применён платформой», и никогда не рисовать «защищено», когда трафик идёт напрямую (ТЗ §6). Механизм на Windows (WFP-фильтры собственного привилегированного сервиса против WNA-профиля против официальной службы WireGuard) не решается умозрительно: **spike S4 в начале цикла E**, и до его результата в документации не появляется ни одного утверждения о Windows kill switch (ТЗ §14 «не объявляй защитные механизмы проверенными, если тесты не выполнялись»).

**Что не заявляем (ТЗ §6 «не заявляй о полной анонимности», ТЗ §13 «не обещай скорость без измерений»):** анонимность (single-hop, IP виден узлу, email при регистрации), абсолютную защиту, конкретные Мбит/с и «минимальную задержку» без замеров на реальной инфраструктуре, post-quantum стойкость, защиту от анализа трафика хостинг-провайдером.

## 9. Тест-стратегия (ТЗ §14)

### 9.1 Unit (без контейнеров, чистый Go)

- argon2id: хэш/верификация, отказ на пустом пароле; JWT: TTL, подпись, `jti` в denylist; refresh: ротация, детект переиспользования → отзыв семьи.
- Валидация ключей: канонический base64 (неканонический отклоняется), длина, `platform` enum, CIDR/порт/MTU диапазоны.
- Парсер/сериализатор конфига: round-trip; **инъекционная стойкость** — host/preshared/DNS-строки с shell-метасимволами, CRLF, вложенными секциями, unicode-обфускацией; проверка, что ни одно серверное значение не попадает в argv без валидации.
- Desired set: детерминированность; свойство (не пример): ни один `revoked`/`expired`/`superseded` за пределами overlap никогда не попадает в desired — проверяется на случайных данных.
- Аллокация адресов: выбор минимального свободного, отсутствие коллизий при конкурентной выдаче, окно переиспользования после отзыва.
- Diff-apply против fake-transport: список операций на добавление/изменение/удаление; пустой diff → ноль обращений к netlink.
- Свёртка телеметрии: дельты пиерных счётчиков → `device_day_traffic`; обработка ребуса узла (счётчики упали → считаем reset, а не отрицательный трафик).
- Матрица авторизации «роль × маршрут»; envelope ошибок; rate limiter на fake-часах; идемпотентность (повтор, конфликт тела, протухший ключ).

### 9.2 Интеграционные (Compose: PostgreSQL 17, Redis 7)

- Миграции `up → down → up`; проверка констрейнтов (двойной активный профиль, уникальный адрес, FK-каскады при удалении устройства).
- sqlc-запросы против реальной БД; транзакция аллокации при конкурентном запросе с N горутин.
- Контракт API ↔ узел: тестовый HTTP-сервер + настоящий исполняемый файл агента (опрос, 304, применение, отчёт, ротация токена).
- Отказы: API недоступен → узел сохраняет set и ставит `stale`; Redis недоступен → fail-open; узел не выходит на связь → `server_health.status='stale'`.

### 9.3 E2E на настоящем туннеле (привилегированный контейнер)

`node1` (агент + unbound + NAT) и `client1` (туннельный клиент) в одной harness-сети, `probe` (сервис «покажи мой egress-адрес») за узлом. Then: выдача → handshake → трафик через узел (egress = адрес узла) → отзыв ≤ 30 с → трафик остановлен → DNS-запрос клиента уходит через recursor узла, off-tunnel резолв не наблюдается → IPv6-путь наружу отсутствует → ротация не рвёт поток (ни одного разрыва в окне overlap) → лимит устройств блокирует четвёртое устройство при лимите 3.

Оговорка, которую надо читать вместе с этим пунктом: harness проверяет **механику** туннеля, NAT, маршрутизации и жизненного цикла доступа. Он не проверяет поведение в интернете у конкретного хостинга, MTU-чёрные дыры на пути и реальную задержку/пропускную способность — это станет известно только на вашем узле, и до тех пор в каталоге эти поля `null`.

### 9.4 Безопасность

`govulncheck` на сборочном Go; сканер секретов в CI (проверяет в том числе, что ни один приватный ключ не попал в фикстуры); ассерт-тест: в ни одном зафиксированном ответе API нет строк, пригодных как приватный ключ узла; проверка, что unbound в роли конфигурируется без journal queries.

### 9.5 Нагрузка (ТЗ §13)

Замеры в harness: 50 узлов × опрос каждые 30 с (≈ 1,7 rps на desired + отчёты), 100 выдач профилей в секунду, p95 latency аллокации адреса под блокировкой. Это измерения локальные, они дают только «держит/не держит», и в панели/доках публикуются с явной пометкой окружения. Нагрузочные на реальной инфраструктуре — F.

### 9.6 Что выполняется вне A и как помечается

Ручные тесты kill switch на реальных устройствах, переходы Wi-Fi↔LTE, выход из сна, поведение на IPv6-only сетях, Windows-клиент — **не выполнялись**. В отчётах и в `docs/testing-status.md` они имеют статус `not-run`, согласно ТЗ §14 и ТЗ §19.12.

Точные версии инструментов фиксируются при первой сборке и затем не меняются молча: `golang:1.25-bookworm` (при недоступности — ближайший доступный stable, зафиксированный в `go.mod` и в `Dockerfile`), PostgreSQL 17, Redis 7.x. Terraform-модули в A не появляются: их назначение (заказ VM) становится понятен только когда есть реальный провайдер, и создавать «универсальный» модуль без провайдера — это и есть фиктивная реализация.

## 13. Известные ограничения (фиксируются как есть, не «баг на потом»)

1. **Квота по одновременным устройствам — с задержкой до применения** (≤ интервал синхронизации), мгновенного отказа лишнему соединению WireGuard не даёт.
2. **Отзыв на недоступном узле применяется с его возвращением.** Окно неопределённо, пока узел не вышел на связь; мера — `drain` для плановых работ и малый интервал опроса.
3. **Компрометация узла раскрывает трафик через него в моменте.** Single-hop, ключ на диске узла (`0600`) читается root'ом хостинга. Это осознанная модель доверия; её усиление — не «шифрование ключа на том же диске» (иллюзия), а другой узел/другой провайдер/multi-hop.
4. **Поля задержки, пропускной способности и загрузки — `null` до реальных замеров** на вашем узле. В панели (C) это статус «нет данных», никогда не «0» и не правдоподобное число.
5. **IPv6-клиент отключается** при подключении: на IPv6-only сетях доступа не будет.
6. **Windows kill switch не реализован и не проверен** до цикла E и исхода S4.
7. **Анонимность не обеспечивается** (email, IP виден узлу, платёж, тайминги).
8. **MTU по умолчанию 1420** — консервативно; на пути с меньшим PMTU наблюдаются чёрные дыры, лечится `probe`-тестом и понижением значения на сервере.

## 14. Решения и отклонённые альтернативы (ADR-карта)

| ADR | Решение | Отклонено и почему |
|---|---|---|
| 001 | Модульный монолит + отдельный процесс агента | микросервисы (запрет ТЗ §10 без необходимости) |
| 002 | Pull-синхронизация desired set, diff-apply, отзыв ≤ 30 с | push на агент (нужен ingress + TLS на каждом узле, больше поверхность); рендер `.conf` + SSH-деплой (нет живых метрик, медленный отзыв) |
| 003 | Access-JWT + denylist в Redis + durable отзыв семьи refresh | opaque-токены на всё (каждый запрос → хранилище, хуже масштабирование ТЗ §13) |
| 004 | [netlink diff-apply через `wgctrl-go`](../../adr/0004-wireguard-peer-apply.md): `ReplacePeers` запрещён, отзыв — `PeerConfig.Remove`, счётчики снимаются до применения. Подтверждено S3 | прямой `genetlink` (не нужен: библиотека умеет штучные операции, измерено); `wg syncconf` через subprocess (shell из управляющего кода против ТЗ §5); full replace каждый цикл (пересоздаёт пиеров, теряет handshake и счётчики) |
| 005 | unbound-рекурсор на узле, `log-queries: no` | DoT-форвардинг (внешняя зависимость, first-hop задержка); публичные резолверы (QNAME третьей стороне) |
| 006 | Агрегат байт на устройство-сутки, пер-пиерные счётчики — только в Redis с TTL | счётчики на профиль/сессию (пары «время+объём» сопоставимы с трассами на выходе); полный отказ от байт-данных (ломает ТЗ §9 «распределение нагрузки») |
| 007 | Отключение IPv6 на клиенте (A) → опционально ULA + NAT66 позже | `::/0` без адреса = тихий blackhole, невозможно диагностировать |
| 008 | Механизм Windows-туннеля не выбирается до S4 | выбор «по аналогии с другими продуктами» — непроверенное утверждение |
