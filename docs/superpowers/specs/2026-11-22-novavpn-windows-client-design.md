**Статус:** проектная спецификация, ожидает ревью заказчика.
**Дата:** 2026-11-22. **Предшественники:** циклы A-1, A-2, A-3 (слиты в `main`, HEAD `4d068e3`).
**Название цикла:** E-1. **Ветка:** `cycle/e1-windows-access-manager`.

**Окружение, проверенное при проектировании:** Windows 11 10.0.26300 x64; .NET SDK 10.0.204; рантаймы `Microsoft.NETCore.App` 10.0.8/10.0.15 и `Microsoft.WindowsDesktop.App` 10.0.8/10.0.15; WebView2 Runtime 157.0.4341.60; Node.js 24.20.0 в PATH; NuGet доступен (X25519 и WebView2-пакеты проверены пробной сборкой); Docker Engine 29.9.3 доступен. Прав администратора нет; драйвер WireGuard не установлен, официальный клиент WireGuard отсутствует. Dev-стенд A-3 на момент проектирования остановлен.

## 1. Границы цикла и критерии приёмки

### 1.1 В объёме E-1

Windows-приложение «менеджер доступа»: самостоятельная регистрация и вход, привязка устройства к аккаунту, просмотр каталога серверов, выдача и отзыв профиля, локальная генерация ключа X25519, сохранение готового `.conf` для официального клиента WireGuard, честное отображение состояний и ограничений. Приложение не поднимает туннель и не управляет сетью.

### 1.2 Вне объёма E-1 (перенесено осознанно)

| Уходит в | Что | В E-1 существует как |
|---|---|---|
| E-2 (после спайка S4) | собственный туннель: WireGuardNT, wintun/wireguard-go, привилегированный сервис, выбор механизма по ADR-008 | `.conf` и инструкция импорта в официальный WireGuard |
| E-2 | kill switch и его наблюдаемое состояние | отсутствует; UI не рисует «защищено» ни в каком виде |
| E-3 | установщик, подпись кода, автообновление, трей и автозапуск | portable-каталог и zip, версия `0.1.0-preview` |
| C | веб-кабинет | публичный API, который клиент уже потребляет |
| D | платежи, смена тарифа, восстановление пароля | экран плана только читает `/me`, действий оплаты нет |
| — | ротация ключа из UI, несколько устройств на одной установке | API ротации существует, но в E-1 клиент ведёт одно устройство на пару «адрес API + аккаунт» |

Заглушек и пустых экранов «на будущее» не создаётся: ТЗ §19.3 запрещает фиктивные реализации вместо работающей логики.

### 1.3 Критерии приёмки E-1

1. Регистрация и вход выполняются из клиента против живого стенда; сессия переживает перезапуск приложения через refresh-токен в DPAPI; выход стирает сессию.
2. Устройство регистрируется по публичному ключу, сгенерированному на клиенте; приватный ключ не появляется ни в HTTP-трафике, ни в JS, ни в журнале. Лимит устройств и дубликат ключа обрабатываются стабильными кодами.
3. Каталог показывает `availability` как есть, а `latency_ms`, `load`, `capacity_mbps` при `null` — как «не измерялось»/«не заявлена», без выдуманных чисел.
4. Профиль выдаётся и отзывается; `server_not_available`, `conflict`, `forbidden` и `404` дают человеческие сообщения по коду, а не общий текст.
5. Экспортированный `.conf` содержит ровно одну строку `PrivateKey`, публичный ключ пары совпадает с зарегистрированным, переводы строк LF, другие строки серверного конфига не изменены. Перед записью показывается предупреждение о секрете в файле.
6. `dotnet test` зелёный; тесты моста доказывают отсутствие токенов и приватного ключа в ответах UI; `--selftest` загружает настоящие ассеты в WebView2 и завершается кодом 0; живой E2E Core проходит на Docker-стенде.
7. Скриншоты UI-ассетов сняты и просмотрены; в инструкции они подписаны как ассеты с заглушкой моста, а не как снимки работающего приложения.
8. `docs/guide/client.html`, `docs/guide/index.html`, `README.md`, `docs/testing-status.md` и ADR-010 обновлены в том же цикле; непроверенное внесено строками `not-run`.
9. Границы честности зафиксированы в UI и документации: клиент не управляет туннелем, установщика и подписи нет, импорт `.conf` в официальный WireGuard на этой машине не проверялся.

### 2.2 Граница UI и хоста

UI загружается из папки через виртуальный origin WebView2 `https://app.novavpn.local/` (`SetVirtualHostNameToFolderMapping` с `DenyCors`). TCP-порт не открывается. Взаимодействие — только сообщения:

```
JS → хост:  {"id":"5b2f6c1e-8a41-4c3d-9d7e-0f1a2b3c4d5e","cmd":"servers.list","args":{}}
хост → JS:  {"id":"5b2f6c1e-8a41-4c3d-9d7e-0f1a2b3c4d5e","ok":true,"data":{"servers":[]}}
            {"id":"5b2f6c1e-8a41-4c3d-9d7e-0f1a2b3c4d5e","ok":false,
             "error":{"code":"server_not_available","message":"Сервер сейчас не принимает новые профили","request_id":"9a1b2c3d4e5f6071"}}
```

Инварианты моста:

1. `AddHostObjectToScript` не используется — только `postMessage`; JS не получает COM-объектов.
2. Команда обязана быть в белом списке; неизвестная команда — отказ `unknown_command`.
3. Размер сообщения ограничен 64 КиБ; глубина JSON и длины строк валидируются.
4. Ответы моста не содержат: access/refresh-токенов, приватного ключа, пароля, полного текста WireGuard-конфига, заголовков Authorization, адреса API с учётными данными.
5. Путь для экспорта выбирает только пользователь в системном диалоге; JS не передаёт файловые пути.
6. Любая ошибка возвращается с `request_id`, если сервер его дал; иначе с клиентским кодом.
7. CSP ассетов: `default-src 'none'; script-src 'self'; style-src 'self'; font-src 'self'; img-src 'self' data:; connect-src 'none'; base-uri 'none'; form-action 'none'`. Сеть из UI запрещена полностью.
8. `NavigationStarting` отменяет переход за пределы виртуального origin; `NewWindowRequested` отменяется. Внешние ссылки (например, установщик WebView2) открывает хост через системный браузер по явному действию пользователя.

## 3. Потоки данных

### 3.1 Вход, регистрация, сессия

1. Первый запуск: поле «Адрес API». Допустим `https://` с любым хостом и `http://` только для loopback (`127.0.0.1`, `localhost`, `[::1]`); иначе отказ с объяснением. Адрес — только origin: схема, хост и необязательный порт; путь, userinfo, query и fragment не допускаются, хвостовой `/` нормализуется. Значение хранится в `settings.json`.
2. `POST /api/v1/auth/register` или `POST /api/v1/auth/login` → `Session`. Пароль проверяется в клиенте по контракту: 10–1024 символа, без обрезки пробелов. Refresh-токен немедленно уходит в DPAPI, access остаётся в памяти. Пароль не сохраняется и не журналируется.
3. `GET /api/v1/me` → email, статус, план (`slug`, `device_limit`, `traffic_quota_bytes`), `devices.live/limit`. `plan = null` показывается как «активного плана нет», а не как ошибка входа; `traffic_quota_bytes = null` — «без квоты», а не ноль.
4. При `401` на защищённом запросе: один single-flight `POST /api/v1/auth/refresh`, сохранение нового refresh **до** повтора, повтор исходного запроса ровно один раз. Повторный `401` или отказ refresh — выход из сессии с сообщением. Параллельные запросы ждут один refresh, а не запускают свои.
5. Выход: попытка `POST /api/v1/auth/logout`; локальная сессия стирается в любом случае, даже если сеть недоступна, иначе «выйти» без связи было бы невозможно. Локальная пара ключей устройства сохраняется, чтобы повторный вход не тратил лимит устройств; отдельное действие «Забыть это устройство» удаляет ключ.
6. Access-токен проактивно не обновляется: обновление происходит по `401`, чтобы не плодить лишние ротации. Это осознанный выбор, а не оптимизация.
7. Запуск с сохранённой сессией: прочитать refresh из DPAPI, выполнить `refresh`, затем `GET /me`. Отказ refresh — сессия стёрта, экран входа. При повреждённом хранилище — сообщение из раздела 4.1.
8. Автоматическое следование редиректам выключено: `3xx` считается ошибкой, чтобы пароль или токен не ушли на другой origin. Повторов на `5xx` и сетевых ошибках нет; повтор — действие пользователя, идемпотентность защищает операцию.

### 3.2 Устройство и ключи

1. Пара X25519 генерируется BouncyCastle на клиенте; приватный ключ 32 байта, публичный — 32 байта в base64 (44 символа с `=`), что совпадает с шаблоном API `^[A-Za-z0-9+/]{43}=$`.
2. Локальная запись устройства привязана к ключу `SHA-256(api_base_url + "\n" + email)` и содержит `device_id` (пусто, пока регистрация не подтверждена), приватный и публичный ключи. На аккаунт и адрес API — одна запись.
3. После входа: `GET /api/v1/devices` — список включает и отозванные, у них заполнен `revoked_at`. Поиск сохранённого публичного ключа идёт только среди живых: найдено живое — используем его `device_id`; сохранённого ключа нет — генерируем пару; совпало только отозванное устройство — сохранённая пара мертва, генерируем новую, потому что занять прежний ключ нельзя: уникальность `(user_id, public_key)` полная, и сервер ответит `duplicate_device`. Живой регистрации нет — `POST /api/v1/devices` с `Idempotency-Key`, `platform=windows`, `name` = hostname (обрезка до 64 символов, непустое). Новая пара сохраняется в DPAPI до запроса, чтобы повтор после сетевой ошибки шёл с тем же ключом; `device_id` дописывается после успешного ответа.
4. `duplicate_device`: перечитать список; живое устройство с нашим ключом — взять его, только отозванное — сгенерировать новую пару и повторить регистрацию один раз. `device_limit_reached`: показать `live/limit` и предложить отозвать другое устройство. `forbidden`: «нет активного плана». `idempotency_key_conflict`: ошибка операции, новый ключ только для нового намерения.
5. Удаление устройства: подтверждение с предупреждением, что профили и сохранённые конфиги перестанут работать; `DELETE /api/v1/devices/{id}`; при успехе — удалить локальную пару.
6. Ротация ключа в E-1 не вызывается: API её поддерживает, но клиент с одним устройством показывает только «пересоздать устройство» через удаление и повторную регистрацию.

### 3.3 Каталог и профиль

1. `GET /api/v1/servers` → список `ServerSummary`. `availability` отображается буквально: `available`, `unknown`. `latency_ms`, `load`, `capacity_mbps` при `null` — «не измерялось» / «не заявлена»; сортировка по выдуманной задержке запрещена.
2. Выдача: `POST /api/v1/devices/{device_id}/profiles` с `{server_id}` и `Idempotency-Key`. Ключ создаётся на пользовательское намерение и переиспользуется при сетевом повторе; после известного исхода (2xx/4xx) новое нажатие — новый ключ.
3. Ошибки: `server_not_available` → «Сервер сейчас не принимает новые профили», перечитать каталог; `conflict` разбирается по `details`: `reason=pool_exhausted` → «На этом сервере не осталось свободных адресов» и предложение выбрать другой; `reason=address_race` → «Выдача не состоялась из-за параллельного запроса, повторите»; без `reason` (профиль уже активен) → перечитать профили и показать настоящий статус; `forbidden` → «устройство отозвано или нет плана»; `404` → «сервер или устройство не найдено»; `429` → время из `Retry-After`.
4. `GET /api/v1/devices/{device_id}/profiles` → статусы `active`, `superseded`, `revoked`, `expired` показываются буквально, без «успеха» вместо отзыва.
5. Отзыв: `DELETE /api/v1/devices/{device_id}/profiles/{server_id}` → `204`. Повторный отзыв `409` с `details.status` показывается как настоящее состояние, а не как успех.

### 3.4 Конфиг и экспорт

1. `GET /api/v1/devices/{device_id}/profiles/{server_id}/config` → `text/plain`, `Cache-Control: no-store`. Запрос выполняется только для профиля в статусе `active`; `409` в ответе на конфиг (статус изменился между чтением профиля и запросом) показывается как настоящее состояние профиля после перечитки, а не как сетевая ошибка.
2. Проверка серверного текста до вставки ключа: UTF-8 без BOM; нет `\r`, `\0`; ровно одна секция `[Interface]` и одна `[Peer]`; нет строки `PrivateKey`; каждая непустая строка вне заголовков секций имеет вид `Ключ = значение`; секции верхнего уровня только эти две.
3. Композиция: строка `PrivateKey = <base64>` вставляется сразу после `[Interface]`; остальные строки сохраняются байт-в-байт; файл заканчивается LF. Публичный ключ пары, из которой взят приватный, сверяется с `public_key` устройства перед записью.
4. Экспорт: системный диалог сохранения, имя по умолчанию `NovaVPN-<server>.conf`, где `<server>` очищен до `[A-Za-z0-9._-]` (пусто → `server`). Перед записью — предупреждение: «В файле приватный ключ. Это секрет; не пересылайте файл и не храните его в общих папках». Запись через `FileMode.Create`, `FileShare.None`, Flush; путь и имя возвращаются UI, содержимое — нет.
5. После сохранения карточка честно говорит: «Конфиг сохранён. Подключение выполняет WireGuard; этот клиент туннелем не управляет». Кнопка «Как подключить» открывает локальную `ui/help.html` с шагами импорта в официальный WireGuard.
6. Текст конфига не попадает в JS, журнал, буфер обмена и не показывается на экране. Копирование секрета в буфер обмена в E-1 не предусмотрено.

### 3.5 Состояния и честность

Допустимые состояния карточки: «нет устройства», «устройство готово», «профиль не выдан», «профиль активен», «конфиг сохранён», «профиль отозван», «профиль истёк», «профиль заменён», «сервер недоступен», «нет связи с API». Состояний «подключено», «защищено», «туннель активен» нет: клиент их не наблюдает. После перезапуска приложения статус профиля перечитывается с сервера; сохранённый файл не считается доказательством работы туннеля.

## 4. Секреты и локальное хранилище

### 4.1 Файлы

`%LOCALAPPDATA%\NovaVPN\`:

| Файл | Содержимое | Защита |
|---|---|---|
| `settings.json` | `schema`, `api_base_url`, размеры окна, выбранное устройство | без секретов; обычный ACL профиля |
| `session.dat` | `schema`, `api_base_url`, `email`, `refresh_token`, `refresh_expires_at` | DPAPI `CurrentUser` с энтропией `NovaVPN/session/v1` |
| `devices.dat` | `schema`, записи `api_base_url`, `email`, `device_id` (может быть пустым), приватный и публичный ключи | DPAPI `CurrentUser` с энтропией `NovaVPN/devices/v1` |
| `logs\client-YYYYMMDD.log` | команда, метод, путь, статус, `request_id`, длительность | ротация 1 МиБ × 3; секреты вычищаются |

Запись атомарная: временный файл в том же каталоге, затем `File.Replace`/`Move`. При повреждении DPAPI-блока приложение не угадывает и не удаляет данные: показывает «хранилище повреждено или принадлежит другому пользователю», предлагает войти заново; испорченный файл остаётся для разбора. Access-токен, пароль и текст конфига на диск не пишутся.

### 4.2 Что не покидает процесс

Пароль, access-токен, refresh-токен (кроме DPAPI-блока), приватный ключ и полный текст конфига не передаются в JS, не пишутся в журнал, не попадают в аргументы команд и не выводятся в сообщениях об ошибках. Журналируется `account_id` из `/me`, а не email. Тесты моста проверяют сериализованные ответы на отсутствие маркеров `eyJ`, `PrivateKey`, `refresh_token`, `password`.

### 4.3 Модель угроз E-1

| Угроза | Ответ E-1 | Остаточный риск |
|---|---|---|
| Злонамеренный или скомпрометированный API | структурный разбор конфига и вставка ключа в C#; UI рендерит данные через `textContent`; CSP запрещает сеть и внешние скрипты; редиректы не выполняются | сервер может выдать валидный, но чужой Endpoint — клиент покажет его в каталоге; проверки принадлежности узла вне E-1 |
| Вредоносное содержимое в WebView | нет `AddHostObjectToScript`, нет навигации по внешним URL, CSP, локальные ассеты | уязвимость самого WebView2 вне контроля клиента |
| Локальный процесс того же пользователя | DPAPI не защищает от кода, работающего под тем же пользователем | это граница ОС; клиент её не расширяет |
| Утечка через журнал или ошибку | вычистка секретов, короткий формат событий, тесты | ошибки сторонних библиотек не логируются целиком |
| Кража `.conf` после экспорта | предупреждение и ответственность пользователя; файл не создаётся автоматически | файл лежит вне клиента и им не контролируется |
| Подмена адреса API | HTTPS обязателен вне loopback; редиректы запрещены; сертификат проверяется системно | пользователь может сам ввести чужой адрес; фишинг вне модели E-1 |

## 5. Ошибки и сообщения

| Код | Поведение UI |
|---|---|
| `invalid_request` | «Проверьте введённые данные» + поле, если известно |
| `unauthenticated` | сессия истекла → экран входа (после единственной попытки refresh) |
| `invalid_credentials` | «Неверный email или пароль» без указания, что именно неверно |
| `refresh_token_invalid` | сессия недействительна → экран входа; локальная пара ключей устройства сохраняется |
| `email_taken` | «Этот email уже зарегистрирован» + ссылка на вход |
| `account_locked` | «Аккаунт заблокирован администратором» |
| `forbidden` | по контексту: «нет активного плана» или «устройство отозвано» |
| `not_found` | «Не найдено» с контекстом операции |
| `conflict` | настоящее состояние из `details`: `status` при отзыве и конфиге, `reason` при выдаче |
| `device_limit_reached` | лимит из `/me`, список устройств, предложение отозвать |
| `duplicate_device` | автоматическая сверка списка, без ошибки пользователю при совпадении |
| `idempotency_key_conflict` | «Операция изменилась, начните заново»; новый ключ только для нового намерения |
| `idempotency_key_in_progress` | «Операция уже выполняется»; повтор с тем же ключом после короткой паузы |
| `server_not_available` | «Сервер сейчас не принимает новые профили» + перечитка каталога |
| `rate_limited` | «Слишком часто. Повторите через N с» из `Retry-After`; авто-повтора нет |
| `internal` | «Внутренняя ошибка» + `request_id` для поддержки |
| `unknown_command`, `bad_args` (клиентские) | «Внутренняя ошибка клиента»; детали только в локальном журнале |
| `network`, `timeout` (клиентские) | «Нет связи с API»; данные не считаются актуальными |

Общий конверт ошибки сервера — `{"error":{"code","message","details","request_id"}}`; `request_id` сохраняется и показывается в диагностике. Сообщения прикладного слоя русские; коды стабильны и не переводятся.

## 6. Проверка

### 6.1 Автоматические уровни

| Уровень | Что доказывает | Где |
|---|---|---|
| Core unit, фейковый HTTP | разбор конверта, `401` → один refresh → повтор, отказ refresh, `429` и `Retry-After`, стабильность `Idempotency-Key`, коды устройств и профилей, вежливость к `null`, отказ `http` вне loopback и `3xx`-редиректу | `tests/NovaVpn.Client.Core.Tests` |
| Core unit, файлы | DPAPI round-trip, повреждённый блок не удаляется, атомарная запись, журнал без секретов | там же |
| Core unit, крипто и конфиг | форма ключа 32/44, публичный ключ выводится из приватного, композиция сохраняет строки, отказы на CRLF/`NUL`/дубле/отсутствии секций/готовом `PrivateKey` | там же |
| App router без WebView | белый список, валидация аргументов, лимит размера, **ответы моста не содержат секретов** | `tests/NovaVpn.Client.App.Tests` |
| `--selftest` | настоящий WebView2 грузит ассеты, CSP не ломает UI, мост отвечает на `app.info`, консольных ошибок нет, процесс завершается кодом 0 | `client/src/NovaVpn.Client.App` + прогон |
| Живой E2E Core | регистрация → устройство → каталог → выдача → конфиг → композиция → отзыв → `409` на конфиг отозванного профиля, против настоящего API и PostgreSQL | `client/tests/NovaVpn.Client.E2E` через `client/scripts/e2e.sh` на dev-стенде |
| UI-кадры | вёрстка состояний и отсутствие горизонтального переполнения на 1440×900, 900×700 и 720×600 (минимальное окно) | Chromium + заглушка моста, кадры в `docs/images/guide/` |
| Гигиена | нет `eyJ`, приватных ключей и паролей в клиентских файлах, журналах и кадрах | сканер по диффу и артефактам |

Живой E2E регистрирует синтетический аккаунт, создаёт через admin API сервер с уникальным именем и переводит его в `online`; работает без узлового агента, потому что выдача профиля и рендер конфига не требуют живого handshake. Администратор создаётся CLI-подкомандой с паролем из stdin, не из argv. Скрипт удаляет за собой профиль, устройство и сервер, а также временные файлы и профиль браузера; серверный dev-стенд остаётся в исходном состоянии. Это доказывает клиентский путь, но не работу туннеля.

### 6.2 Что остаётся `not-run`

- Импорт `.conf` в официальный WireGuard for Windows и реальный handshake: официальный клиент и драйвер на машине отсутствуют, прав администратора нет.
- Установка и работа из установщика, подпись кода, обновление.
- Поведение на Windows 10, на машине без WebView2 Runtime, на другом пользователе Windows (DPAPI другого профиля).
- Сквозная работа туннеля через клиент: появится в E-2 после S4.
- Пиксельная проверка GUI агентом: агент не видит отрисовку окна; вместо этого `--selftest` и кадры ассетов, которые просматривает человек.

## 7. Поставка

1. `dotnet publish client/src/NovaVpn.Client.App -c Release -r win-x64 --self-contained false -o client/dist/win-x64` → каталог `client/dist/win-x64/` (git-игнор), zip `NovaVpn-Client-0.1.0-preview-win-x64.zip`.
2. Требования: Windows 10/11 x64, WebView2 Evergreen Runtime, .NET Desktop Runtime 10. При отсутствии WebView2 приложение показывает инструкцию и ссылку на официальный установщик; молчаливой установки зависимостей нет.
3. Подписи нет: SmartScreen предупредит; это указано в README и в инструкции.
4. Версия `0.1.0-preview` отображается в шапке и в `app.info`. Автообновления и фоновых служб нет.
5. Воспроизводимость: `packages.lock.json`, фиксированные версии, `dotnet restore --locked-mode`, `dotnet test` и `dotnet publish` в отдельной Windows-джобе CI. `--selftest` в CI не запускается: там нет WebView2 и интерактивной сессии; это фиксируется как `not-run`, а не как успех.

## 9. Риски и открытые вопросы

| Риск | Как снижается | Что остаётся |
|---|---|---|
| Скриншоты UI с заглушкой принимают за работающее приложение | подпись в инструкции, `--selftest` и живой E2E Core | отрисовку окна подтверждает только человек |
| GUI нельзя запустить и снять из агента | `--selftest` без скриншотов, прямой запуск exe как дымовой тест | пиксельные дефекты ловит визуальный просмотр |
| WebView2 отсутствует у части пользователей Windows 10 | проверка при старте и понятное сообщение | установка остаётся за пользователем |
| BouncyCastle и WebView2 как supply-chain | фиксированные версии, lock-файл, лицензии в репозитории | будущие CVE требуют отдельного обновления |
| DPAPI привязан к пользователю и машине | явное ограничение в документации | переноса секретов нет и не планируется |
| Пользователь считает сохранённый `.conf` доказательством защиты | честные состояния и help-страница | фактическое подключение вне клиента |
| HTTP-адрес стенда закрепляется в продукте | поле адреса без значения по умолчанию; `http` только для loopback | пользователь может ввести неверный адрес |

Открытых вопросов, блокирующих E-1, нет. Вопрос собственного туннеля, kill switch и установщика относится к E-2/E-3 и решается после спайка S4 и ADR-008.
