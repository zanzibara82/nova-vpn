# S1 и S3: WireGuard в контейнере и семантика применения набора пиеров

Дата: 2026-10-20. Статус: оба спайка выполнены, ответы зафиксированы в ADR-004.
Код стенда — одноразовый, лежит в `.scratch/spikes/wg-s3/` (вне git) и не является
частью продукта; раздел «Как повторить» ниже воспроизводит эксперимент заново.

## Условия, в которых измерялось

| Параметр | Значение |
|---|---|
| Ядро | `6.18.54.1-microsoft-standard-WSL2` (общее для всех WSL2-дистрибутивов и Docker-VM) |
| Docker | Docker Desktop, daemon 29.8.2, Compose 5.6.0 |
| Образ узла | `alpine:3.20` + `iproute2`, `wireguard-tools`, `iputils`; сборка на `golang:1.24-alpine` |
| Библиотека | `golang.zx2c4.com/wireguard/wgctrl v0.0.0-20241231184526-a9ab2273dd10` |
| Топология | 3 контейнера в одной bridge-сети `172.30.0.0/24`: node-a (измеряющий), node-b, node-c; туннельная сеть `10.90.0.0/24` |

## S1 — вывод: привилегированный контейнер не нужен, достаточно `CAP_NET_ADMIN`

1. Модуль загружается на уровне хоста: `wsl -u root modprobe wireguard` даёт
   `wireguard 90112 0`, плюс зависимости `libcurve25519`, `libchacha20poly1305`.
   В `/boot/config-*`: `CONFIG_WIREGUARD=m`, `CONFIG_TUN=m`. Под uid 1000 `modprobe`
   отказывает (`Operation not permitted`) — загрузка модуля остаётся шагом с root.
2. `ip link add dev wg0 type wireguard` в контейнере с **одним только** `--cap-add NET_ADMIN`
   проходит успешно. Контрольный прогон с `--cap-drop ALL` даёт `RTNETLINK answers: Operation not
   permitted`, то есть требование capability подтверждено, а не предполагано.
3. `/dev/net/tun` в контейнере **отсутствует**, и это не мешает: WireGuard-устройство
   создаётся ядром по netlink, а не через TUN-символьное устройство. Значит агенту не
   нужны ни `--device /dev/net/tun`, ни `--privileged`.
4. `wgctrl.New()` и `ConfigureDevice()` работают изнутри контейнера: первый вызов
   26–56 мс (установка приватного ключа и listen-порта). Последующие per-peer
   операции — 83–810 мкс, полный replace набора — 0.84–1.36 мс.

Итог для развёртывания: `cap_add: [NET_ADMIN, NET_RAW]` (NET_RAW нужен проверкам связности через `ping` в
harness и, на реальном узле, MASQUERADE-диагностике), `privileged: false`,
`devices:` пустой. Загрузка модуля — ответственность образа хоста (Ansible-роль),
а не контейнера.

## S3 — вывод: полная перезапись набора пиеров пересоздаёт каждый пиер

Это и был главный риск цикла A. Измеряли двумя сигналами, потому что ни один по
отдельности не доказателен: таймстемп handshake можно спутать с «пересоединился сам»,
а счётчики rx/tx обнуляются только при уничтожении объекта пиера.

### A/B: один и тот же цикл синхронизации, два способа применения

Desired set меняется только для пиера C (переключаем persistent-keepalive; на цикле 7
C отзывается, на цикле 9 возвращается). Пиер B не меняется вообще и несёт непрерывный
трафик (`ping -i 0.05`, 400 пакетов).

| Метрика | diff-apply (per-peer, `ReplacePeers=false`) | full replace (`ReplacePeers=true`) |
|---|---|---|
| B: переподключений (new handshake) | **0 / 12** | **12 / 12** |
| B: откат счётчиков rx/tx | 0 / 12 | 4 / 12 (пила 860 → 988 → 860) |
| C: переподключений при повторной отправке того же пиера | **0 / 10** | н/д |
| B: handshake по всем циклам | константа `1792510097739434791` | скачет каждый цикл |
| B: rx | монотонно 2268 → 11100 | пила 860 → 988 → 860 … |
| Потерянных ICMP | 0 из 400 | 0 из 400 |
| Стоимость вызова | 83–810 мкс | 0.84–1.36 мс |

Три следствия, каждое важно по-своему:

- **`ReplacePeers=true` пересоздаёт пиеров, даже когда конфигурация байт-в-байт
  совпадает с живой.** Handshake-состояние и счётчики при этом теряются. Фоллбэк
  «уходим в прямой genetlink» из §4.2 спецификации не нужен: задача решается тем,
  чтобы просто не отправлять неизменённых пиеров.
- **Per-peer операции в `wgctrl-go` обновляют пиера на месте.** Повторная отправка
  C с изменённым полем не сбрасывает его handshake и не откатывает счётчики —
  то есть библиотека ведёт себя так же, как `wg(8)`. Это проверено и независимо:
  `wg set wg0 peer <pub> persistent-keepalive 20` оставил handshake пиера
  без изменения (`1792509866179929226` до и после), а счётчик tx продолжил расти.
- **Отзыв работает штучно.** `PeerConfig{PublicKey: …, Remove: true}` при
  `ReplacePeers=false` убирает ровно одного пиера за ~0.5 мс: список 2 → 1,
  соседний пиер сохраняет handshake и счётчики, маршрут до отозванного адреса
  становится `Destination Host Unreachable` немедленно. Повторная выдача
  восстанавливает связность в том же цикле.

### Побочный, но обязательный к учёту результат: байтовый учёт

Поскольку пересоздание пиера обнуляет rx/tx, collector не может читать счётчики
«когда удобно»: любое применение diff, которое пересоздаёт пиера (ротация ключа,
смена endpoint, смена allowed-IP), стирает набранные с прошлого снятия байты.
Правило для имплементации: **снять счётчики до применения изменений, а не после**,
и при обнаружении отката считать его пересозданием, а не аномалией. Иначе ТЗ §9
«распределение нагрузки по локациям» и агрегаты «байт на устройство-сутки» (ADR-006)
систематически недоучитывают трафик, и недоучёт тем больше, чем чаще ротации.

### Чего эксперимент НЕ показал (не переносить в продукт как доказанное)

- Потерь трафика не наблюдали ни в одном режиме. Аргумент против full replace —
  не «обрыв соединения», а хаос handshake и потеря счётчиков. Заявлять обратное было бы
  невыдавленным фактом.
- Ядро — WSL2, а не продакшн-дистрибутив; оба конца туннеля в одной хост-машине,
  без реального RTT, без NAT между пиерами, без вариации MTU, без конкуренции за CPU.
  Цикл-тест обязателен к повтору на реальном VPS до того, как эти цифры будут
  считаться эксплуатационными.
- Два пиера, а не тысячи. Поведение при 1000+ пиеров и полном наборе не измерялось.
- End-to-end задержка отзыва через API (заявленные ≤ 30 с) не измерялась — здесь
  проверена только узловая половина, вызов netlink.

## Как повторить

Стенд одноразовый; для воспроизведения без `.scratch/` достаточно этих шагов.

```sh
# 0. хост: модуль (WSL2)
wsl -u root modprobe wireguard

# 1. сеть и три узла (минимальные права)
docker network create --driver bridge --subnet 172.30.0.0/24 wg-spike-net
docker run -d --name node-a --network wg-spike-net --ip 172.30.0.10 \
  --cap-add NET_ADMIN --cap-add NET_RAW wg-spike:0 …   # b, c = .11, .12

# 2. на node-a: создать устройство, warm-up, затем замер
docker exec node-a spike up
docker exec node-a spike cycle            # diff-apply
docker exec node-a spike cycle-replace    # full replace
```

Ожидание, если среда та же: `diff` — 0 переподключений неизменённого пиера,
`replace` — переподключение на каждом цикле.
