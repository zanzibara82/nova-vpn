# Инцидент на узле

Правило чтения: сначала снимаются факты, потом действия. Любое действие до снятия
этих данных уничтожает причину первого сбоя, и разбор начинается заново, но уже
без улик.

## 1. Зафиксировать факты до действий

```bash
ssh root@HOST "systemctl status novavpn-node-agent --no-pager"
ssh root@HOST "journalctl -u novavpn-node-agent -n 100 --no-pager"
ssh root@HOST "wg show wg0"
curl -sS -H @~/novavpn-admin-auth.header \
  "https://api.novavpn.example/api/v1/admin/servers/$SERVER_ID"
```

Ожидание: четыре снимка сохранены (вывод службы, 100 строк журнала, состояние
интерфейса, поле `health.status` из API). Пустой вывод — тоже факт, его записывают.

## 2. Узел не выходит на связь

Признак: `health.status = stale` при живом процессе агента. Смотрят журнал:

```bash
ssh root@HOST "journalctl -u novavpn-node-agent -n 200 --no-pager | grep -E 'узел: |TLS|настройка|сокета|цикл узла'"
```

Ожидание: как минимум одна реальная строка узла. Рабочий цикл агента пишет ровно
один вид строк — предупреждение с префиксом `узел: ` и названием операции. Полный
перечень держит исходник (`internal/nodeagent/runtime/runner.go`, семнадцать вызовов
помощника `failure`), переписывать его сюда нельзя: он устареет при первой же правке
цикла. Для отказа связи нужны эти: `узел: получение желаемого набора не удалось`,
`узел: получение снимка не удалось`, `узел: применение желаемого набора не удалось`,
`узел: отправка heartbeat не удалась`, `узел: ответ 304 без условного запроса`,
`узел: набор предназначен другому узлу`, `узел: чтение состояния не удалось`,
`узел: узел не зарегистрирован`. Остальные девять относятся к ключам, токенам и
записи состояния (`узел: чтение приватного ключа не удалось`, `узел: преобразование
желаемого набора не удалось`, `узел: запись применённого набора не удалась`, `узел:
повторная запись токена не удалась`, `узел: ротация токена не удалась`, `узел:
неверный ответ ротации токена`, `узел: запись нового токена не удалась`, `узел:
отправка отчёта о состоянии не удалась`, `узел: шаг завершился с ошибкой; цикл
продолжится`) и видны тем же фильтром по префиксу. Строки `desired set`,
`certificate` в журнале узла не бывает: английский текст с `desired set` принадлежит
серверной части.

Отказы доверия сертификата видны узлом в двух местах, и оба русские:

- при старте — проверка конфигурации и сборки клиента
  (`services/node-agent/cmd/novavpn-node-agent/main.go`): `TLS:
  NOVAVPN_NODE_ALLOW_INSECURE_API разрешена только при NOVAVPN_NODE_ENV=dev`,
  `настройка API/TLS не удалась: проверьте NOVAVPN_NODE_API_URL и
  NOVAVPN_NODE_CA_FILE`, `не задана настройка NOVAVPN_NODE_API_URL`;
- в рабочем цикле — только как одна из строк `узел: ` выше: подробности TLS-рукопожатия
  агент в журнал не выносит, их печатает сервер.

Фильтр по префиксу не покрывает строки шагов настройки (`регистрация узла не
удалась`, `узел не инициализирован`, `стартовый токен не задан`): они относятся к
`init` и `enroll`, а не к рабочему циклу. Полный разбор — тот же `journalctl -u
novavpn-node-agent -n 200 --no-pager` без фильтра.

Где искать серверные сообщения: `novavpn-api serve` пишет JSON-журнал в свой
поток ошибок, а не на узел; отказ вычисления набора там выглядит как
`nodeapi: desired set compute failed` и `nodeapi: desired set etag failed`
(`internal/nodeapi/handlers.go`). Этот журнал читает тот, кто запустил API: в этом
цикле развёртывание API на реальном хосте не автоматизировано и остаётся за задачей 19.

Статус `stale` с 2026-11-05 шире, чем «API недоступен»: истинный признак ставится
при любом незавершившемся цикле сходки (отказ получения набора, отказ снимка, отказ
применения) — формулировка и обоснование в датированной записи ADR-009. Поэтому по
одному `stale` не различают, кто именно отказал, и смотрят строку `узел: `.

Агент **не** перезапускают до прочтения журнала: после перезапуска причина первого
сбоя в журнале уже не находится.

## 3. Узел потерян или скомпрометирован

```bash
curl -sS -X POST -H @~/novavpn-admin-auth.header \
  "https://api.novavpn.example/api/v1/admin/servers/$SERVER_ID/node-token/revoke"
```

Ожидание: `204`, и в аудите запись `node_token_revoked`. Отзыв гасит узловые токены,
поднимает `config_version` и переводит сервер в `draining` — пиеры снимаются на
следующем опросе.

Новый узел ставится по `node-deploy.md` **с новым ключом**: у существующего сервера
`public_key` не меняется, поэтому под новый узел создают новый сервер, а старый удаляют
тогда, когда у его профилей не осталось адресов (`DELETE` живым профилям отказывает).

## 4. Смежные случаи

- скомпрометирован ключ устройства пользователя — `revoke-a-key-now.md`;
- нужно немедленно остановить вход в аккаунт —
  `POST /api/v1/admin/users/{id}/lock` возвращает `200` с числом отозванных профилей и
  серверов: новые выдачи и ротация refresh останавливаются сразу, уже выданный access
  живёт до истечения TTL (не больше 10 минут, ограничение §13).

## 5. Итог инцидента

Строка в журнал операций: время, `server_id`, `reason` из аудита, какие шаги
выполнены. Если какая-то проверка инцидента не выполнялась — в
`docs/testing-status.md` она остаётся `not-run`, а не исчезает из таблицы.
